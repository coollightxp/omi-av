# 版本台账 · 基线重建（2026-11-13）

## 背景

Windows 实测：v2.0.7 正常，v2.0.8 起出现「几乎铺满窗口、四周一圈蓝边、中间纯白」
的白块；出现/消失与底部面板的自动隐藏计时同步，白块期间底部面板看不见。

对比 v2.0.7（`53c658ac`）与 v2.0.8（`642453bd`）全部 106 个源文件，只差 2 个文件
95 行，且不含任何绘制覆盖层的代码 → 判定问题来自 2.0.8 之后的某一批界面改动
（用户下载的 2.0.8 很可能是 06:28 那批，含「定时关闭在画面上可见」的覆盖层）。

**处置方式：以 v2.0.7 源码树为干净基线，逐批回加 2.0.8 之后的功能，每批单独出包，
由用户逐版实测定位。**

### v2.1.21 · 第十四批：亚洲粤语台「总出错」根因修复（AAC 坏包容错）

| 文件 | 改动 |
|---|---|
| `lib/services/media/omi_video_io.dart` | `open` 前设 `demuxer-lavf-o=err_detect=ignore_err`：包一层 `_applyFaultTolerance`，在 `initialize()` 里 await 后才 open（AVOption 在 open 时读一次） |
| `lib/services/media/omi_video_mdk.dart` | fvp 注册参数加 `avformat.err_detect=ignore_err`，MDK 引擎同步容错 |

- **根因**（实测数据）：AsiaFM 亚洲粤语台 `http://yyt.asiafm.net:8000/asiafm` 是 Icecast 2.4.4 的 `audio/aacp`（AAC-ADTS 裸流，96kbps），流里混着结构损坏的包——ffprobe 报「PCE 采样率索引与容器配置不符 / Reserved bit set / Pulse tool not allowed」，mpv 进一步报 `aac: channel element 2.12 is not allocated` → `Error decoding audio` → 上层判播放失败。坏包出现是随机的，所以表现为「有时能播、有时切过去就报错」，且与播放引擎无关（两套引擎都基于 ffmpeg 系解码，同样失败）
- **验证**：`ffmpeg -err_detect ignore_err` 连续解码 8 秒，astats 输出 RMS -8.88dB、Peak 1.88dB、0 个 NaN/Inf → 音频本身完好，只是被判 corrupt；对照实验确认只有 demuxer 层参数有效（`--ad-lavc-o` 无效）
| `lib/services/player_controller.dart` | 错误判定从「一次 error 即判死」改为**延迟复检**：起播 8 秒内给 3.5 秒宽限、播放中 2.5 秒，期间只要「在播 / 位置推进」就判为误报；若界面已落到错误页则自动恢复（`_recoverFromSoftError`，OSD 提示「已恢复播放」并清零重试计数） |

- 副作用评估：只把「轻微损坏即整段失败」改成「跳过坏包继续放」，正常流无影响
- **第二层修复（用户实测反馈）**：这个台的毛病不只是解码失败，而是「声音一直在放，界面却弹重试卡片、重试三次后进错误页」。根因是错误判定对起播阶段太严——起播瞬间 `state` 还不是 playing、`position` 还是 0，条件不满足就直接进重试链路。加上延迟复检 + 自动恢复后，这类「假报错」不会再打断观看
